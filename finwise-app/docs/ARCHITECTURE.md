# 系统架构与原理

## 1. 整体结构

FinWise 当前是一个 Next.js 前端、Supabase 后端、Vercel 托管的预测市场 MVP。

```text
用户浏览器
   │
   ├── 页面与交互 ── Next.js / React
   │
   ├── 注册登录 ──── Supabase Auth
   │
   └── 数据请求 ──── Supabase REST / PostgreSQL
                         │
                         ├── RLS：限制用户只能看自己的数据
                         └── RPC：在一个数据库事务中完成下单

GitHub main ──自动部署──> Vercel ──> ycsc-chi.vercel.app
```

## 2. 为什么使用这些技术

### Next.js

- 同一项目可同时承载用户端、管理端和以后增加的服务端接口。
- Vercel 可直接从 GitHub 自动构建和发布。
- React 状态适合目前的交互式移动端原型。

### Supabase

- Auth 负责密码哈希、会话和用户身份，项目代码不保存明文密码。
- PostgreSQL 负责持久化账户、市场、订单、持仓和账本。
- RLS（行级安全）在数据库层限制数据访问；即使前端代码被修改，用户也不能读取其他人的持仓。
- SQL 迁移文件保存每次数据库变化，便于审核和重新部署。

### Vercel

- GitHub `main` 更新后自动构建。
- 公开配置以环境变量注入，不硬编码在页面组件中。

## 3. 注册登录原理

1. 用户提交用户名、邮箱和密码。
2. 浏览器调用 Supabase Auth。
3. Supabase 安全存储密码摘要，不向项目返回密码。
4. `auth.users` 新增用户后，数据库触发器 `handle_new_user` 自动建立 `profiles` 资料和初始模拟余额。
5. 登录成功后，浏览器保存短期会话令牌，并使用令牌访问受 RLS 保护的数据。

邮箱确认目前临时关闭。重新开启后，未确认邮箱的用户不能首次登录。

## 4. 预测下单原理

下单不能只在前端执行，因为用户可以修改浏览器代码。当前通过数据库函数 `place_order` 原子执行：

1. 确认用户已经登录。
2. 检查预测金额不低于最低值。
3. 锁定并读取市场，确认市场存在、开放且未截止。
4. 锁定用户资料，检查余额。
5. 计算价格和份额。
6. 写入订单。
7. 新建或累计持仓。
8. 扣减模拟余额。
9. 写入不可省略的账本记录。

这些操作处于同一个 PostgreSQL 事务中。任何一步失败，所有步骤一起回滚，不会出现“扣了余额但没有持仓”。

## 5. 持仓与结算

- “持仓中”读取 `positions` 并关联 `markets`。
- 当前价值 = 份额 × 当前对应方向价格。
- “已结算”只显示状态为 `settled` 的市场。
- 结果方向等于用户方向时显示“预测成功”，否则显示“预测失败”。
- 当前还没有自动结算服务；需由管理后台确认结果并执行后续结算事务。

## 6. 真实资金边界

当前界面单位为“模拟 USDT”，仅用于测试预测与结算逻辑。它不是真实链上 USDT，不连接区块链，也不允许真实充值提现。接入真实资金前必须完成司法辖区、牌照、KYC/AML、托管、支付安全和审计评估。
